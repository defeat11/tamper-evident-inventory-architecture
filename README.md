# tamper-evident-inventory-architecture

[English](README.en.md)

**قطعة عتاد تدخل المستودع ← مستند برقم متسلسل بلا فراغات، وحركة في سجل ترفض قاعدة البيانات نفسها تعديله.**

> **هذا النظام يعمل في بيئة إنتاج لدى جهة عملي، والكود ملكها. هذا المستودع يوثّق المعمارية والقرارات الهندسية وطريقة البناء.**

نظام عهد ومخزون لقسم تقنية المعلومات في 2,705 أسطر PHP (خادم Laravel).
فيه 50 نقطة نهاية، و22 جدولاً، و4 تريغرات SQL تفرض عدم قابلية التعديل.
كل استلام وصرف وإرجاع ينتج مستنداً مرقّماً وقيداً في دفتر للإضافة فقط.

---

## المشكلة

عهد الأجهزة تُدار عادة في جداول Excel قابلة للتعديل بأثر رجعي.
عند خلاف على عهدة، لا يوجد إثبات أن السجل لم يُلمس.

والحماية في كود التطبيق وحدها لا تكفي.
من يصل لملف قاعدة البيانات يتجاوز التطبيق كله بسطر SQL واحد.

والمدقق يسأل سؤالاً واحداً قاتلاً: لماذا في تسلسل المستندات فراغ؟
فراغ واحد في الترقيم يعني احتمال مستند محذوف.

المطلوب: سجل يرفض التعديل حتى من داخل قاعدة البيانات، وترقيم لا ينتج فراغات أصلاً.

## كيف يشتغل

### 1) دفتران للإضافة فقط — والفرض من محرك قاعدة البيانات نفسه

دفتر `movements` يسجل 8 أنواع حركة: استلام، صرف، إرجاع، صيانة خارجة وعائدة، إتلاف، نقل، تسوية.
ودفتر `audit_logs` يسجل أفعال المستخدمين من 28 موضع تسجيل في الكود.

الحماية ليست شرطاً في الكود، بل 4 تريغرات داخل SQLite — منقولة حرفياً من المهاجرة:

```sql
CREATE TRIGGER trg_audit_logs_no_update BEFORE UPDATE ON audit_logs
BEGIN SELECT RAISE(ABORT, 'audit_logs is append-only'); END;

CREATE TRIGGER trg_audit_logs_no_delete BEFORE DELETE ON audit_logs
BEGIN SELECT RAISE(ABORT, 'audit_logs is append-only'); END;
```

والزوج نفسه على `movements`. تجربة حقيقية على نسخة من قاعدة النظام، بوصول مباشر بلا تطبيق:

```text
UPDATE audit_logs SET action='HACKED' WHERE id=1;  → Error: audit_logs is append-only
DELETE FROM audit_logs WHERE id=1;                 → Error: audit_logs is append-only
```

### 2) ترقيم متسلسل بلا فراغات

جدول `doc_sequences` يحمل عدّاداً لكل (نوع مستند، نطاق، سنة) خلف قيد فريد.
حجز الرقم يحدث داخل المعاملة نفسها التي تنشئ المستند وحركاته.
لو فشل أي سطر، ترجع المعاملة كلها ويرجع العدّاد معها — فلا يضيع رقم.

والنظام لا يملك أصلاً أي مسار حذف للمستندات: 0 نقاط حذف على الاستلام والصرف والإرجاع.
التصحيح يكون بقيد معاكس (حركة تسوية ADJUST)، فيبقى التاريخ كاملاً.
صيغة الرقم: `GRN-2026-0001` — النوع ثم السنة ثم عدّاد من 4 خانات.

### 3) معاملة واحدة لكل عملية

سند الاستلام مثالاً: الرقم والسطور ووحدات المخزون والحركات كلها في `DB::transaction` واحدة.
فلا يوجد مستند بلا حركة، ولا حركة بلا مستند، ولا رصيد يخالف دفتره.

## أهم قرار في التصميم

**المشكلة:** سجل تدقيق يفرضه كود التطبيق يسقط أمام أي وصول مباشر لقاعدة البيانات.
مدير نظام، نسخة احتياطية مسرّبة، جلسة صيانة — كلها تعدّل التاريخ بصمت.

**القرار:** إنزال الفرض إلى أدنى طبقة ممكنة: تريغرات داخل محرك قاعدة البيانات.
ترفض UPDATE وDELETE على الدفترين مهما كانت هوية المتصل وأداته.

**التكلفة والعائد:** التكلفة أن الخطأ لا يُصحح بتعديل بل بقيد معاكس يبقى ظاهراً.
والعائد أن المدقق يتحقق من الحماية بسؤال واحد لجدول `sqlite_master`.
وتجاوزها يتطلب فعلاً صريحاً (DROP TRIGGER) يترك أثراً — لا تعديلاً صامتاً.

## حدود الآلية بصدق

- من يملك صلاحية تغيير المخطط يستطيع إسقاط التريغرات ثم إعادتها. الآلية تجعل العبث فعلاً مقصوداً مكشوفاً، ولا تجعله مستحيلاً رياضياً. سلسلة تجزئة أو نسخ WORM هي الخطوة التالية لو ارتفع التهديد.
- `lockForUpdate()` بلا مفعول في SQLite؛ الضامن الفعلي للعدّاد هو كاتب SQLite الوحيد. الكود يبقى صحيحاً عند الانتقال إلى MySQL أو Postgres لأن القفل يصبح حقيقياً هناك.
- تسجيل أفعال المستخدمين يبتلع فشله بتحذير — قرار إتاحة قبل اكتمال. دفتر الحركات بعكسه: داخل المعاملة، وفشله يُسقط العملية كلها.

## ماذا في هذا المستودع

الكود ملك جهة العمل، فليس هنا. بنية النظام في الإنتاج:

```
backend (Laravel + SQLite)
  migrations    مهاجرة 262 سطراً: 18 جدولاً + 4 تريغرات، و4 جداول لطبقة رؤية AI
  Services      5 خدمات: الترقيم، التدقيق، الاستلام، توليد الوسوم، الرؤية
  Controllers   15 متحكماً خلف 50 نقطة نهاية
  Models        23 نموذج Eloquent
  Middleware    فصل صلاحية الكتابة عن صلاحية الإدارة
frontend        React + Vite + Ant Design بواجهة عربية RTL
```

الأدوار 3: مدير، أمين مستودع، مُطالِع — وكل الكتابة خلف وسيط `CanWrite`.

## لماذا بنيته

أعمل مشرف تقنية معلومات، وعهد الأجهزة كانت جداول تُعدَّل بأثر رجعي بلا أثر.
الآن 8 أنواع حركة تدخل دفتراً واحداً ترفض قاعدة البيانات نفسها تغييره.
